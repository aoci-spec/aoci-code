# Release Supply Chain

This repository includes non-publishing package validation for the current
release candidate. `.goreleaser.yml` keeps remote release creation disabled,
and the validation workflow has
read-only repository permissions. Publishing is a separate authorized action.

## Artifact set

A release candidate artifact set consists of:

- platform archives built with CGO disabled, `-trimpath`, an empty Go build ID, the full source commit, and a source-derived commit date;
- `SHA256SUMS` using SHA-256;
- exactly one per-archive SPDX JSON SBOM generated by the pinned Syft version;
- GoReleaser `artifacts.json` build metadata;
- `RELEASE-MANIFEST.json`, which hashes and classifies every artifact and binds the Git commit, dirty state, toolchain identities, and current Managed Scope, Apply-authorization, policy-bound Receipt, and cognition-budget machine contracts. The verifier reads legacy `aoci-release-artifact-manifest/v2`; the current generator emits `v3`.

The release-manifest generator rejects a dirty source tree by default, verifies
the declared commit against Git, rejects symlinks, requires an exact
archive-to-SBOM pairing, sorts relative paths, writes atomically, and can verify
a downloaded artifact directory without network access:

```bash
go run ./scripts/release/manifest --verify dist/RELEASE-MANIFEST.json
```

GoReleaser's checksum file may cover a narrower publishable set than the release
manifest. `make release-check` verifies every `SHA256SUMS` subject, then verifies
the manifest's independent digest and size binding for the complete artifact
directory. Consumers should verify both.

## Reproducible-build posture

The recipe removes host paths and wall-clock build time, fixes the source commit timestamp, disables CGO, and records exact tool identities. A release must also pin the Go patch version, build from a clean immutable tag, verify modules, and compare binaries from at least two isolated builders before claiming bit-for-bit reproducibility.

The current release-candidate validation establishes repeatable inputs and
evidence. Its artifact manifest v3 binds the reviewed MCP tools/list protocol
and current lifecycle contract versions. It does not claim that two independent
builders produce identical archives.

## Database driver dependency audit

Database Evidence support uses two reviewed pure-Go direct dependencies:

| Module | Pinned version | License | Purpose |
| --- | --- | --- | --- |
| `github.com/jackc/pgx/v5` | `v5.10.0` | MIT | PostgreSQL `database/sql` driver |
| `github.com/go-sql-driver/mysql` | `v1.10.0` | MPL-2.0 | MySQL `database/sql` driver |

The pinned `go-licenses` v1.6.0 gate enumerates every reachable external Go
package after `go mod verify` across the complete Linux, macOS, and Windows
release matrix, rejects an unknown external license, and rejects AGPL, GPL, or
SSPL dependencies. It also requires the exact release-binary module/version
union to match `THIRD-PARTY-NOTICES`. Local AOCI packages can be reported as
`Unknown` because dependency scanners do not classify the main module; those
rows are not interpreted as third-party dependency licenses.

The current release-binary union contains 18 modules. The authoritative pinned
inventory, license-file hashes, retained license texts, and the MCP Go SDK's
Apache-2.0 transition with residual MIT contributions and CC-BY-4.0
documentation classification are recorded in `THIRD-PARTY-NOTICES`. Both
database-driver paths build with `CGO_ENABLED=0`.

MPL-2.0 is file-level and compatible with this dependency use, but binary
distribution must still carry the required third-party notices and a compliant
way to obtain the covered driver source.

## Signing and provenance proposal

For a future public release, use keyless Sigstore/cosign identity backed by the project's GitHub Actions OIDC identity, sign `SHA256SUMS` and `RELEASE-MANIFEST.json`, and generate GitHub artifact attestations for the checksum subjects. Verification documentation must pin the repository owner, workflow identity, and expected certificate issuer.

Do not enable signing or provenance permissions until the public repository, release workflow path, protected environment, and publisher identity are approved. The validation workflow intentionally has no `id-token`, `attestations`, or `contents: write` permission.

## Remaining hardening before public release

- pin every third-party GitHub Action to a reviewed full commit SHA and automate reviewed updates;
- approve the publisher identity and incident/revocation procedure;
- run independent rebuild comparison and document archive normalization results;
- retain release logs, SBOMs, attestations, signatures, and the exact workflow source;
- review SBOM coverage and third-party license obligations;
- require an explicit human approval environment before any publish job.
