# Release Supply Chain

This repository separates non-publishing package validation from the authorized
Tag release path. `.goreleaser.yml` does not publish remotely; the dedicated
`.github/workflows/release.yml` workflow owns keyless signing, provenance,
Release-asset validation, and publication.

## Artifact set

A signed release-candidate upload consists of exactly 16 assets:

- six platform archives built with CGO disabled, `-trimpath`, an empty Go build
  ID, the full source commit, and a source-derived commit date;
- exactly six per-archive SPDX JSON SBOMs generated by the pinned Syft version;
- `SHA256SUMS`, covering those 12 distributable subjects;
- `RELEASE-MANIFEST.json`, which hashes and classifies the Release assets and
  binds the Git commit, dirty state, toolchain identities, and current Managed
  Scope, Apply-authorization, policy-bound Receipt, and cognition-budget machine
  contracts;
- `SHA256SUMS.sigstore.json`, the Cosign bundle for the checksum file; and
- `AOCI-CODE_v0.1.0-rc2.provenance.sigstore.json`, the GitHub build-provenance
  bundle for the 12 distributables, `SHA256SUMS`, and
  `RELEASE-MANIFEST.json`.

GoReleaser's local `artifacts.json` is build metadata, not a Release upload.
The signed-release manifest v4 schema distinguishes the 12 checksum subjects,
14 provenance subjects, signature bundle, and provenance bundle. The signature
bundle cannot be a subject of the checksum file it signs, and the provenance
bundle cannot attest to itself. The verifier retains read compatibility with
the earlier non-publishing v2 and v3 manifest schemas.

The release-manifest generator rejects a dirty source tree by default, verifies
the declared commit against Git, rejects symlinks, requires an exact
archive-to-SBOM pairing, sorts relative paths, writes atomically, and can verify
a downloaded artifact directory without network access:

```bash
go run ./scripts/release/manifest --verify dist/RELEASE-MANIFEST.json
```

`make release-check` verifies every `SHA256SUMS` subject, then verifies the
manifest's independent digest, size, and archive-to-SBOM bindings. The signed
Tag workflow additionally fails closed if any of the 16 declared Release assets
is missing, extra, misclassified, or inconsistent with the provenance subject
set. Consumers should verify the checksum, signature, provenance, and manifest.

## Reproducible-build posture

The recipe removes host paths and wall-clock build time, fixes the source commit timestamp, disables CGO, and records exact tool identities. A release must also pin the Go patch version, build from a clean immutable tag, verify modules, and compare binaries from at least two isolated builders before claiming bit-for-bit reproducibility.

The current release-candidate validation establishes repeatable inputs and
evidence. Its artifact manifest v4 binds the reviewed MCP tools/list protocol
and current lifecycle contract versions. It does not claim that two independent
builders produce identical archives.

## Database driver dependency audit

Database Evidence support uses two reviewed pure-Go direct dependencies:

| Module | Pinned version | License | Purpose |
| --- | --- | --- | --- |
| `github.com/jackc/pgx/v5` | `v5.10.0` | MIT | PostgreSQL `database/sql` driver |
| `github.com/go-sql-driver/mysql` | `v1.10.0` | MPL-2.0 | MySQL `database/sql` driver |

The pinned `go-licenses` v1.6.0 gate enumerates every reachable external Go
package after `go mod verify` across the complete Linux, macOS, and Windows
release matrix, rejects an unknown external license, and rejects AGPL, GPL, or
SSPL dependencies. It also requires the exact release-binary module/version
union to match `THIRD-PARTY-NOTICES`. Local AOCI packages can be reported as
`Unknown` because dependency scanners do not classify the main module; those
rows are not interpreted as third-party dependency licenses.

The current release-binary union contains 18 modules. The authoritative pinned
inventory, license-file hashes, retained license texts, and the MCP Go SDK's
Apache-2.0 transition with residual MIT contributions and CC-BY-4.0
documentation classification are recorded in `THIRD-PARTY-NOTICES`. Both
database-driver paths build with `CGO_ENABLED=0`.

MPL-2.0 is file-level and compatible with this dependency use, but binary
distribution must still carry the required third-party notices and a compliant
way to obtain the covered driver source.

## Keyless signing and provenance

The publisher is the GitHub Actions OIDC workload identity of
`aoci-spec/aoci-code/.github/workflows/release.yml`. The workflow installs the
pinned Cosign v3.1.3 tool and signs the original `SHA256SUMS` bytes with
`cosign sign-blob --bundle=SHA256SUMS.sigstore.json --yes`. This creates an
ephemeral keyless signature and does not create, store, or use a long-lived
private key, PAT, or GPG signing key.

Tag verification requires this exact certificate identity:

```text
https://github.com/aoci-spec/aoci-code/.github/workflows/release.yml@refs/tags/v0.1.0-rc2
```

The required OIDC issuer is:

```text
https://token.actions.githubusercontent.com
```

The same workflow uses GitHub Artifact Attestations to generate SLSA build
provenance for exactly 14 subjects: the six archives, six SBOMs,
`SHA256SUMS`, and `RELEASE-MANIFEST.json`. The resulting bundle is uploaded as
`AOCI-CODE_v0.1.0-rc2.provenance.sigstore.json`. Verification constrains the
repository, exact workflow certificate identity, Tag ref, and Tag commit in
addition to each subject digest.

A manual dry-run on `main` performs real GitHub OIDC signing and attestation but
publishes only an Actions Artifact. Its certificate identity ends in
`@refs/heads/main`; its exact identity is:

```text
https://github.com/aoci-spec/aoci-code/.github/workflows/release.yml@refs/heads/main
```

That branch identity is deliberately not accepted as the Tag release identity.
The shared supply-chain job has `actions: read`, `contents: read`,
`id-token: write`, and `attestations: write`; this lets the branch dry-run sign
and attest but not publish. For a Tag run, the read-only Actions permission also
lets the workflow require successful Fast CI, Full Confidence, Release
Rehearsal, and signed-release dry-run evidence for the exact current `main`
commit. A separate `v*`-Tag-only publish job has `contents: write` and
`attestations: read`, but no OIDC signing permission. This split prevents the
dry-run path from obtaining Release publication authority.

The executable consumer verification order is documented in
[Installation](install.md): download all 16 assets, verify `SHA256SUMS`, verify
its exact keyless publisher identity with Cosign, verify the 14 GitHub
provenance subjects, inspect the matching SBOM, and perform offline manifest
verification.

Artifact attestations establish who built particular bytes, from which
repository, workflow, ref, and commit. They are not a guarantee that the
software is free from vulnerabilities. This release also makes no claim of
bit-for-bit reproducibility, a personal or enterprise hardware-key signature,
or SLSA Level 3.

## Ongoing hardening

- review and update pinned third-party GitHub Action SHAs deliberately;
- maintain a publisher-identity incident and revocation procedure;
- run independent rebuild comparisons before making a reproducibility claim;
- retain release logs, SBOMs, attestations, signatures, and the exact workflow
  source;
- periodically review SBOM coverage and third-party license obligations.
