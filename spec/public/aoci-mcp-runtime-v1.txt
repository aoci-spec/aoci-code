AOCI-CODE MCP Runtime Contract v1
=================================

Transport and identity
----------------------

`aoci mcp` runs an MCP server over stdio. `serverInfo.name` is `aoci-code` and
`serverInfo.version` is the version injected into the running binary. Stdout is
reserved for JSON-RPC frames. Logs and diagnostics are written to stderr.

The current MCP protocol identity is `2025-11-25`.

Tool surface
------------

The public server exposes exactly these nine tools:

  aoci_get_entries
  aoci_header
  aoci_maintain
  aoci_overview
  aoci_remove_entry
  aoci_report
  aoci_rules
  aoci_search
  aoci_update_entry

The SHA-256 identity of the sorted names, joined by LF with a final LF, is:

  b4a56cb6d4e625189708e2132a45094eecc62a05c6a1bd4d06ddd0471598176e

Schemas and behavior
--------------------

The tool descriptions and input schemas returned by the running server are the
machine contract. Tools resolve the repository passed to the server and load
current repository state for each call. A protocol error is returned as an MCP
error result; it is not printed as a second stdout message.

The nine-tool identity is independent from optional CLI lifecycle commands.
Changing a CLI command does not implicitly add, remove, or rename an MCP tool.

`aoci_update_entry` has an exclusive optional `target_index` mode. Its only
accepted value is `aoci.code.target.txt`; it cannot be combined with single or
batch Entry fields. The target itself remains non-authoritative and carries no
source digest. During the call, Go joins current Code debt with target Entry
changes and explicit `#Target-Reuse: code:<path>` declarations, computes and
lock-rechecks final source SHA-256 values, and enters the existing atomic batch
pipeline. Success synchronizes the target from formal Code. Any incomplete or
unsafe binding returns a stopped result whose fallback is ordinary Maintain.
This mode changes neither the nine tool names nor their identity hash.

Optional module cognition
-------------------------

`aoci_rules` has one additive optional string input, `module_path`. Omitting it
returns the existing runtime Rules text unchanged. In a Volumes v1 repository,
providing it appends one `AOCI Project Module Cognition JSON:` marker followed
by the complete selected `project-module-cognition/v1` projection. Every call
loads and validates a fresh coherent snapshot; the server does not retain
module memory or return load, reuse, refresh, replace, epoch, or reset state. A
module request is limited to 50 Code objects and Legacy layout returns an
explicit error.

An ordinary `aoci_overview` request still defaults to `requested_scope=all` and
`effective_scope=all` and delivers the complete Whole-Index through the existing
inline or continuation transport. A module request has no state to reset and
never changes Overview content, scope identity, receipts, refresh state,
Challenge, Attestation, or the stable nine-tool name identity.

For a successful ordinary Overview, model-visible `content` contains only the
exact framed cognition body. Transport and state fields are returned in
top-level `_meta` for the Host. `overview_delivery.chunk_tokens` defaults to
600000 and permits 4000 through 600000. A fitting single response ending at
`BODY_END` requires no model confirmation, Attestation, or extra AOCI reply;
an explicitly smaller multi-Chunk configuration retains Host-driven cursor and
proof compatibility.
