AOCI Runtime Contract (session level)

AOCI provides models with stable, versioned, incrementally maintainable repository-level cognition. The complete index describes system architecture, managed-object responsibilities, important relationships, external contracts, and critical constraints. Current source, tests, configuration, database structures, and other runtime facts remain the evidence for concrete implementation. AOCI complements rather than replaces source reading, LSP, CodeGraph, and other structured tools, and it does not dictate the user's architecture, algorithms, test methods, or implementation order.

This contract entered current context through aoci_rules. Do not call aoci_rules again within the same cognition cycle unless the contract is no longer reliably present or the AOCI service identity changes.

Authority boundary: this contract defines only session-level principles for establishing, reusing, communicating, and maintaining cognition. The current Guide carries the execution order and safety stops for the current Plan. Tool Schema, public Spec, Validator, and deterministic state machine carry machine structures, criteria, and runtime results. Prompt governs model semantic generation only. MCP Description, CLI Help, AGENTS, README, and static documentation provide necessary guidance for their entry points but cannot override those machine facts. Machine numbers, vocabularies, and sets come only from internal/machinecontract in the currently compiled version, never from historical contracts, Golden files, or experimental Prompts.

Fresh Bootstrap authoring boundary: use the existing persistent Onboarding progression. The Host model authors Root, Meta, tags, and F/R/A/S from current evidence, supplies its authoring-run declaration, and binds it to the current Plan, Evidence, and complete Candidate. AOCI may compute bindings and validate the receipt but must never set origin=host_model, manufacture a Host receipt, or generate semantic content. Internal batches proceed automatically and are not user decisions; the existing approval, safety, drift, CAS, and Recovery boundaries remain authoritative.

1. Establishing, reusing, and restoring cognition

1. At the start of a normal Agent Run, read aoci_rules once and request aoci_overview. When it reports continuation_required=true, do not ask the user, state a partial system conclusion, or start the business task. Submit the exact next_cursor and continue automatically until completed=true. Stop the cognition chain on Host truncation, a missing, duplicate, or reordered Chunk, cursor error, Index change, or chunk_tokens change. Before Attestation completes, never use Memory, source, Spec, aoci.txt, historical sessions, scope, search, or Entry reads to repair or supplement Whole-Index cognition. If Host truncation occurs, tell the user to set overview_delivery.chunk_tokens to a smaller valid value and restart; do not change it automatically. The challenge ordinal is the 1-based position in the formal Entry sequence. Header content, comments, blank lines, Section/Overview/Chunk markers, receipts, and Metadata are excluded; Chunk Receipt first_entry_ordinal and last_entry_ordinal use the same sequence. The Attestation must echo the Challenge's exact current index_sha256, entry_sequence_sha256, and entry_count; a prior Index, Entry sequence, count, or Attestation is invalid. After all Chunks, submit the existing model-cognition-attestation/v1 once. One correction is allowed only for a same-response JSON Schema or field-format error and must not change semantic answers. An object, Tag, or F mismatch means model_attestation=fail and cognition_assimilation=uncertain, with no semantic retry or information bypass. It disables an unqualified complete-system claim, but honest answers and task-bound source, test, Spec, and engineering work may continue. Initial failure also blocks Root/Meta, Migration, layout-wide, and other unbound system decisions. A context-compaction refresh with complete transport, unchanged cognition identity, aligned governance, and no Recovery or third-party conflict consumes its generation even when Attestation is partial or failed; continue the existing source-bound task without another automatic Overview. system_mastery_percent self-assesses only system-framework mastery—architecture, module responsibilities, strong relationships, stable external contracts, and high-entropy safety and maintenance constraints—not all source, branches, identifiers, tests, current runtime state, or permission to edit without reading source. Keep machine Index coverage separate. On success, normally say only: “Fully read and verified AOCI: <entry_count>/<entry_count> Entries, about <estimated_tokens> tokens, <chunk_count> Chunks, Challenge <passed>/<total>, Index coverage <coverage_percent>%; my system-framework mastery—architecture, responsibilities, strong relationships, stable contracts, and critical constraints—is about <system_mastery_percent>%.” On failure, normally say only: “AOCI complete read failed: received <received>/<total> Chunks, Index coverage about <coverage>% because <reason>; complete system-framework cognition cannot currently be claimed.” A successful full response establishes a cognition receipt bound to runtime_repository_root, index_sha256, mcp_service_version, and cognition_scope. Codex Memory and historical Skills may only help recover experience, user preferences, and investigation directions after the formal acceptance boundary. They cannot replace a cognition receipt matching the current AOCI identity. Project AGENTS, current AOCI identity, source, and runtime facts take precedence.

1a. Interpret the additive cognition level independently from the strict proof fields: no_cognition means no valid Index; index_loaded means cognition content is present but delivery is not confirmed; delivery_verified means the Index was loaded and Host delivery was confirmed but strict complete-cognition verification is unfinished; cognition_verified adds a passing 10/10 Attestation; cognition_governed additionally requires governance alignment. When delivery_integrity=confirmed but Attestation is partial, failed, or absent, say that project cognition was loaded and delivery verified but complete cognition verification is unfinished. Never describe that state as no cognition or as failure to understand the system. The generic complete-read failure sentence applies only to an actual delivery fault.

1b. A Host may explicitly request the additive cognition-state/v2 Overview projection. When present, its model_cognition_level ends at model_cognition_usable. Treat delivery_verified, model_cognition_usable, strict_attestation_verified, governance_aligned, and current_system_cognition_reliable as independent facts: strict Challenge ordinal, object identity, Tag, or core F mismatch does not by itself prove that model cognition is unusable. Only current_system_cognition_reliable=true permits an unqualified current complete-system cognition claim. The projection is read-only, changes no receipt or Apply decision, and is omitted unless requested; when absent, use the legacy contract unchanged.

2. After that first complete Overview, keep reusing it while the receipt remains reliable. AOCI checkpoint assessment recognizes context_compaction when the host reports compaction or the model knows the system-wide view was lost; semantic_threshold when the machine-counted, deduplicated semantic changes reach the team setting cognition_refresh_threshold; and phase_transition when one major work phase has completed and another begins. These facts advise the Agent but do not deny an explicit cognition request. Repository root, index_sha256, service identity, scope growth, elapsed time, token totals, risk paths, tool calls, tests, and small steps are not independent checkpoint reasons.

3. A phase_transition means a substantial boundary such as implementation to system testing or one independent workflow to another. It does not mean one function, one test run, one tool call, or another small step. A clean phase transition does not by itself recommend retransmission. The Agent still decides whether it needs another explicit scoped or complete Overview.

4. The host or Agent declares context_compaction and phase_transition through the optional aoci_overview input and supplies refresh_event_id for idempotency. AOCI does not pretend to detect host compaction. semantic_threshold is machine-derived and cannot be declared by the host. Multiple simultaneous reasons merge into one checkpoint assessment.

5. The unique semantic count is current real Stale files plus Actionable Missing files plus Pending Curation files, deduplicated by repository-relative path. Proven format-only and LineEndingOnly changes, Curation exclusions, deterministic technical skips, Git-ignored files, AOCI runtime assets, files restored to Baseline, and objects outside governance do not count. The project value is reported as the cognition_refresh_threshold machine fact below; repositories without the field use the machine default.

6. If checkpoint facts show semantic changes or other alignment blockers, finish the nearest stable work unit, complete formatting, lint and required tests, call aoci_maintain once, handle repair_required or stopped exactly as returned, and prove alignment through Verify, Check, and Guide. An ordinary Overview may still deliver the complete formal cognition while dirty, but it marks that body unreliable; current source, tests, configuration, and database evidence remain implementation truth. Never maintain repeatedly during unstable edits.

7. Machine checkpoint results use refresh_not_required, refresh_required, refresh_deferred_until_stable, or refresh_ready_for_overview. Only check_only=true returns those compact facts without a cognition body. Every ordinary explicit aoci_overview call delivers the complete requested scope when a coherent snapshot is available, even when the same receipt already exists or no reason is pending. One complete, host-confirmed and governance-aligned Attestation attempt consumes the merged reasons and advances the generation. A passing Attestation records a reliable receipt; a partial or failed Attestation records an uncertain receipt and delivery_guidance=full_system_claim_disabled_source_bound_task_continuation_allowed. Neither outcome automatically loops Overview in the same generation.

8. While complete cognition remains reliable, its state is valid and recall is zero. For a local file, module, relationship, or constraint uncertainty, inspect current source first, then use aoci_get_entries or aoci_search only when needed. Dirty formal cognition may be fully delivered but remains invalid as current implementation cognition. Pending recovery or an incoherent cognition snapshot fails closed without a full body.

2. When no usable complete index exists

5. If aoci_overview cannot provide a usable complete index, or only a minimal skeleton exists, the Header is incomplete, Entries are unfinished, or required Curation is undecided, do not treat incomplete content as complete repository cognition and do not use aoci_maintain as a substitute for full-index establishment.

6. Enter the current AOCI Guide and let Guide choose the next stage from actual repository state. Execute only the bound commands and safety stops returned by the current Guide. Do not guess PATH or reconstruct the state machine. Continue until a usable complete Overview is available. Follow the relevant Guide, tool description, and `--help` for platform invocation, request encoding, batch limits, and recovery details.

3. Model-generated, model-read cognition

7. AOCI uses a model-generated, model-read cognition loop. When generating or revising the Header, the model follows the current Guide to investigate repository facts and establish project rules, tag dictionaries, and calibration examples. When generating or updating an Entry, the model first reads the current Header, then the target source, tests, configuration, database structure, other managed facts, and necessary related evidence, and generates cognition item by item.

8. Paths, filenames, extensions, an AST, symbol lists, dependency scans, regular expressions, templates, or rule engines may only help locate, transport, validate, audit, and write facts. They must not directly generate, prefill, assemble, or rewrite tags, F/R/A/S, or Curation decisions.

9. The complete index establishes a high-density cognition map of system position, responsibilities, relationships, contracts, and non-obvious constraints. Exact fields, identifiers, call chains, and implementation behavior still require verification through source, tests, configuration, database structures, LSP, or other structured evidence. When the index disagrees with current facts, verify implementation from current facts and maintain stale cognition when closing the task.

4. Ordinary development and user communication

10. Complete ordinary development according to the user's request and the repository's existing architecture, rules, and verification methods. AOCI must not become the center of work beyond the user's task and must not choose architecture, algorithms, investigation order, implementation method, test strategy, branch strategy, or technology stack for the model.

11. User-visible messages for an ordinary task focus on understanding the request, source investigation, implementation, tests, risks, commits, and worktree state. Do not proactively narrate internal cognition establishment, state detection, or maintenance by default. When the user asks, answer accurately and concisely. In a long-running auto task, a status, explanation, architecture, or timing question is not cancellation: preserve the current Plan, Run, candidates, commit, and CI identity, then resume from the existing next_action without asking the user to say “continue.” Only an explicit stop, pause, cancel, rollback, scope change, or prohibition on commit or Push changes execution. This Host-Agent interpretation rule creates no persistent conversation-task state. When a real blocker, conflict, approval, human decision, safety risk, or unrecoverable runtime failure occurs, report the necessary facts accurately.

12. When the user limits only business-file scope and does not explicitly forbid repository-managed assets, task closing may update AOCI-managed assets such as aoci.txt and Baseline. Distinguish them from business files in audits and commits. When the user explicitly forbids changes to aoci.txt, .aoci, metadata, or any additional file, obey that restriction, do not write, and report remaining inconsistency accurately.

5. Task closing and incremental maintenance

13. A purely read-only question, analysis, version check, or task that changes no AOCI-managed object does not require a maintenance-tool call.

14. When managed objects change, call aoci_maintain exactly once after business edits, formatting, tests, Lint, and required quality checks are complete and the task has reached its final stable state. Do not maintain files one by one in an intermediate state.

15. If a result has aligned=true and status=applied and also reports refresh_status=refresh_ready_for_overview, do not repeat maintenance or writes. Complete the required Verify, Check, and Guide alignment proof; the Agent then decides whether its next phase needs an ordinary complete Overview. Otherwise stop immediately when the tool says no further handling is required. When the tool handles format-only, do not regenerate semantics.

16. If aoci_maintain returns actual candidates, use the dictionaries and calibration examples from the current reliable Header. If current context lacks a reliable Header, call aoci_header first. Then read every affected object and necessary related evidence in full, preserve every source_sha256, candidate_id, and domain batch identity, and submit the complete candidate set for the current machine-issued batch once through aoci_update_entry entries. max_entries limits one request and atomic transaction only. If remaining is nonzero, Apply this batch, call Maintain again against the new preimage, and continue. Never slice a returned batch or reduce Managed Scope because of transport, batch, payload, token, or request limits.

17. If repair_required contains findings, repair only the candidates explicitly identified by findings, keep every other candidate unchanged, and resubmit the same complete batch with a bounded retry. stopped ends that write attempt, not automatically the user task. In auto mode, inspect failed_step, error, formal-write evidence, and Recovery: record a proven zero-write closure and obtain a fresh Plan; Resume a complete Intent with provable postimage; or complete a policy-selected Rollback with exact preimage and replan. Stop the user task when proof is unavailable, third-party bytes conflict, bounded replanning cannot converge, approval or external action is required, or another real safety boundary applies. Never bypass conflicts, approvals, permissions, human decisions, CAS, or safety signals.

18. When evidence is insufficient, use aoci_report and do not guess. aoci_report does not replace Curation, orphan decisions, or failure recovery. If any managed object changes after maintenance completes, the previous result is invalid; complete closing again from the new final stable state.

6. Specialized contracts

19. For the detailed formats, stages, requests, platform differences, and commands of full-index generation, Header, Entries, Curation, human review, orphan decisions, and failure recovery, follow only the current Guide, tool descriptions, model Prompt, and CLI Help. This contract does not duplicate those specialized manuals and must not reconstruct their state machines.

20. Commit the index to Git and review it through ordinary Diff. Cognition written for later models must be based on current evidence, necessary, and reusable. Wrong cognition is more harmful than temporary absence.
