AOCI-CODE CLI Runtime Contract v1
=================================

Identity
--------

The installed binary is named `aoci`. The canonical Go module is
`github.com/aoci-spec/aoci-code`. The command tree and the exact flags exposed
by the current binary are discoverable through `aoci --help` and command-level
`--help` output.

Global behavior
---------------

`--repo` binds an invocation to a repository root. `--json` selects the
machine-readable output for commands that support it. `--quiet` suppresses
eligible human progress output; it does not change the result or authorization
boundary.

The stable process exit classes are:

  0 success
  1 drift or ordinary check failure
  2 invalid input, index, or governance state
  3 uninitialized repository, configuration, or parameter failure
  10 internal failure

One `--json` invocation emits at most one top-level business result or error
envelope. Human-readable errors are written to stderr. The `aoci mcp` command
uses a direct stdio protocol path described by the MCP runtime contract.

`update-entry` accepts exactly one of `--entry` or `--stdin`. The stdin path
uses the existing 16 MiB Entries request limit and consumes at most one byte
beyond that limit to classify oversize input. Read failure or oversize input
returns exit class 3 before Index, Baseline, transaction, or recovery writes.

State and writes
----------------

Command help and the live Guide identify whether an operation is observational,
prepares a candidate, requires human interaction, or can update formal assets.
An observational command does not modify the formal index or Baseline unless
its contract explicitly says otherwise, but local audit evidence can still be
written when enabled. Formal writes use the existing validation, lock, CAS,
atomic-write, and recovery pipeline.

Compatibility
-------------

Automation must consume JSON fields, schema versions, exit classes, and live
capability output instead of parsing human prose. A public contract change that
alters these surfaces requires matching compatibility tests.

`status --deep`, `index inventory`, `index score`, and `index agent plan` are
Legacy-only and reject Cognition Volumes with exit class 3. Existing Legacy
success behavior is unchanged. Volumes maintenance uses Verify, Check, the
current Guide, and ordinary no-argument `aoci_maintain`.

Initialization modes
--------------------

`aoci init --cognition project` is the new-project model-authored path. It
installs configuration, initial Managed Scope and Budget policy, Agent rules,
and runs the selected Host integration adapter (supported adapters write Host
configuration; reference-only adapters retain their documented boundary),
leaves formal cognition and Baseline absent,
then starts the existing persistent Fresh Onboarding session. Its returned next
action is authoritative; scan is not part of this pre-Bootstrap path.

`aoci init --cognition generic` explicitly selects the fixed generic Volume
starter. It fails closed when an Onboarding session has not been aborted, a
Baseline or formal cognition asset exists, an approval artifact or pending
transaction is present, or Recovery is pending. Omitting `--cognition`
preserves the previous init behavior for compatibility.

Fresh Host transport
--------------------

The JSON returned by the active Fresh Session is the executable Host contract.
For each action, the Host consumes the versioned `next_action_contract`, uses
its exact command and machine-filled request template, and preserves all
Session, Batch, Task, Plan, Evidence, and expected-preimage identities. It must
not derive request fields from human prose or treat the compact `next_action`
label as a complete schema.

The contract remains authoritative across context-budgeted authoring batches
and action changes. Host-authored semantic fields and the Host-issued run
identity stay model-owned; AOCI supplies their required shape and bindings but
does not fill them. Candidate payload binding follows the exact read-only
validation action returned by the contract. The Host copies the resulting
machine digest into Candidate provenance before invoking the returned Preview
action; it neither imports AOCI implementation code nor reimplements the digest.

Transport decoding is strict. A rejected request reports no formal write and
the Host may make only the correction allowed by the returned contract. It does
not abandon the active Session, change lifecycle routes, or substitute MCP
tools that require an initialized formal index.
