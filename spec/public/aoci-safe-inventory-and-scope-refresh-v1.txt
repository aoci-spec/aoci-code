AOCI Safe Inventory v2 and Baseline Scope Refresh v1
=====================================================

Status and authority
--------------------

This specification defines the source-discovery safety boundary.
`internal/fs/safe_inventory.go` is the executable path-classification
authority. The existing Baseline v1, global cognition lock, AtomicWriteCAS,
Ledger, and cognition transaction directories remain the only persistence and
recovery authorities.

Baseline Scope Refresh v1 is retired since 0.2.0-rc2: the `baseline scope`
commands and `internal/scoperefresh` are gone, and no binary produces or
advertises its artifact versions. Managed Scope v2 is the one authority for
role-bearing Baseline changes, observe fingerprints, Entry additions/removals,
Retention Review, and cognition budgets. It reuses this safety and persistence
core; it does not create a second Baseline or transaction kernel. See
`aoci-managed-scope-and-budget-v1.txt`.

Safe Inventory v2
-----------------

`safe-inventory/v2` combines Git facts, project configuration, Curation, and a
built-in hard safety boundary. A Git repository contributes tracked paths,
non-ignored untracked paths, and ignored path names using Git's own ignore
semantics. A non-Git root retains a secure name-only traversal for the paths
outside any Git repository below it; a directory below it that holds a `.git`
entry is a child repository, read through its own Git under the same boundary
checks, so its tracked, non-ignored untracked, and ignored paths enter the
inventory container-relative and its `.gitignore` holds. The container stays a
non-Git root: `child_repositories` and `child_repository_roots` are additive
facts, the Baseline keys stay container-relative, and a gitlink inside a child
names a boundary as it does under a Git root. New non-ignored source files
remain eligible; governance is not limited to tracked files.

Managed Scope may ask Safe Inventory to retain otherwise-safe Git-ignored
names as policy candidates. Their bodies remain unread until a winning index
or observe role requires a fingerprint. Hard safety exclusions always run
first and cannot be reopened by this option.

A Git-ignored directory whose every path is already a hard exclusion (a
built-in generated, runtime, or VCS directory name, or a configured excluded
directory) is reported as a single exclusion entry for that directory, and Git
is not asked to list what is beneath it. Every other Git-ignored path,
including an ignored file inside an untracked directory and every file in an
ignored directory without such a name, is reported individually as before, so
this changes no candidate, opt-in, rule outcome, or identity. A Git version
that cannot report directories this way falls back to the per-file listing.

Before any candidate file is opened or hashed, the inventory rejects unsafe
relative paths, symbolic links, junctions/reparse points exposed as unsafe
objects, non-regular files, and cross-platform case-folding collisions. It
then applies built-in exclusions for secret variants, private keys and
credentials, runtime state, dependency trees and framework caches whose names
never denote source (`node_modules`, `__pycache__`, `.next`, `.nuxt`,
`.output`, `.cache`), log/PID/socket files by suffix, database data
files/directories, PM2 and `pids` state, AOCI Draft/transaction/Evidence/Ledger
runtime content, the `.codegraph`
tool runtime, platform temporary files, binary databases, and named
third-party distribution output. Empty `.gitkeep` repository placeholders are
generated artifacts. `.env.example`-style templates are not secret variants.
`package-lock.json` is not a built-in secret or runtime exclusion.

The built-in secret-name rule has two rule sets, selected by the team
configuration key `sensitive_name_rules`. `v1` is the original set: `.env`
and its `.env.<name>` variants, named credential files, private keys, and
`secrets.*`. `v2` adds the shapes operational repositories use for
credentials: a file name with an `env` component after its first component
(`prod.env`, `manager-login.env`, `api.env.local`), and a credential word
(`credential`, `credentials`, `secret`, `secrets`, `password`, `passwords`,
`passwd`, `apikey`, `apikeys`, `token`, `tokens`, or the pair `api-key` /
`api_key`) as a whole word of a file name whose extension is a data or
configuration extension or that has no extension. Under `v2` a name ending in
`.example`, `.sample`, `.template`, or `.dist` is a template, whatever
precedes the suffix, where `v1` exempts only `.env.<name>` templates; a source file such as `tokenizer.go` or `password_hasher.go` is never
matched, because the rule reads names and never content; and a directory
keeps the `v1` classification. The selected set enters the rules identity:
an absent key is `v1` and leaves an existing repository's identity
unchanged, new initialization persists `v2`, and changing the key on an
initialized repository is a governed Scope Change whose coverage reduction
requires approval. A binary that does not know the key evaluates such a
repository under `v1` and answers `scope_change_required`.

Generated build and test output, uploads, backups, caches, and vendored trees
are not a built-in rule: a directory name that can denote source as well as
an artifact is governed by project configuration. New initialization persists
ambiguous names (`backup`, `backups`, `build`, `cache`, `coverage`, `dist`,
`target`, `tmp`, `uploads`, `artifacts`, `vendor`, `logs`, `run`) in `exclude_root_dirs`,
which matches the first directory under the repository root and any
Git-ignored directory of that name at any depth, so a tracked nested module
is source while a generated tree is an artifact wherever it sits. `exclude_dirs` keeps its
any-depth component matching for other names and for repositories initialized
before this policy. Existing repositories retain their persisted lists and
opt in only through a Scope Change. Other nested Git-ignored paths retain the
default Exclude role unless an explicit Managed Scope rule includes them; a
configured exclusion of either list is a hard exclusion no rule overrides.
A configured exclusion names the `exclude_root_dirs`, `exclude_dirs`, or
`exclude_files` entry that produced it; an absent `exclude_root_dirs` list does not
change an old repository's Safe Inventory rules identity.

An excluded file's body is not read and no content SHA is calculated. It does
not enter model prompts, the Baseline, Evidence, Candidates, or Ledger body.
Receipts may contain only the path summary, safety category, rule source,
tracked flag, and aggregate counts.

A tracked excluded path remains visible in review_visible_count, but exclusion
without opening the body is not by itself an Auto blocker. A
project may name an exact sensitive-file path in the high-risk opt-in list,
including a Git-ignored path; globs and unsafe paths are forbidden. Runtime,
generated, AOCI/VCS, and unsafe filesystem objects cannot use this exception.
Opt-in makes the sensitive file eligible, preserves the review-visible count,
and increments auto_blocker_count because the workflow expands into a
sensitive-data read.
Project include/exclude and Curation decisions remain separate authorities and
existing configuration remains readable.

The deterministic summary reports Git tracked, non-ignored untracked,
ignored (a collapsed directory counts once), built-in sensitive, runtime, generated, configured and unsafe-object
exclusions, final managed candidates, review_visible_count,
auto_blocker_count, the compatibility required_human_review projection, rules
identity, and inclusion/exclusion identity. required_human_review retains its
v2 audit meaning for existing Managed Scope and Scope Refresh consumers; Fresh
Auto authorization never uses it as the sole stop condition.

Business Source Manifest
------------------------

`business-source-manifest/v1` is the shared read-only source identity for
authoring, review, Migration, Auto, and tests. It contains sorted paths and one
raw-byte SHA/size/line-ending-policy record per included file, the Safe
Inventory rules and selection identities, Curation identity, optional Git
HEAD, aggregate algorithm, aggregate SHA, and the Inventory summary.
`generated_at` is audit metadata and is excluded from the aggregate identity.
The aggregate algorithm is `sha256-nul-domain-separated-v1`. It performs no
network access.

Baseline Scope Refresh v1 (retired)
-----------------------------------

The machine family baseline-scope-plan/v1, baseline-scope-preview/v1,
baseline-scope-approval/v1, baseline-scope-apply-result/v1,
baseline-scope-recovery/v1, and baseline-scope-status/v1 was the transition
for single-role Baselines before Managed Scope. It is retired since 0.2.0-rc2:
no command produces these artifacts, the capability manifest and the release
manifest no longer list them, and a `scope-<id>.json` intent of that family
left under `.aoci/transactions` reads as an invalid scope receipt until it is
moved out. Managed Scope v2 (`aoci-managed-scope-and-budget-v1.txt`) is the
transition, and it keeps what this family established: scope changes and
source changes are independent, a changed or missing source is never
converted into a scope removal, an ordinary reduction needs a person's
approval, and Apply replays the exact Preview under the global cognition lock
with one immutable recovery Intent and AtomicWriteCAS over the Baseline.

Compatibility
-------------

Baseline v1 remains the read/write format. Existing `config.json` excludes and
line-ending policy continue to apply. Legacy, Volumes, Git, and non-Git
repositories share the same safe discovery boundary. Safe Inventory does not
alter model ownership of Root, Meta, tags, or F/R/A/S.

Managed Baselines add an optional role to each fingerprint; an omitted role is
legacy index. `scan --force` cannot wash or advance a role-bearing Managed
Scope receipt.
