S-Field and Entry Writing Discipline (English rendering)

The Chinese `s-field-discipline.txt` remains the normative original; this file
is its English rendering and adds no second rule authority. Machine authority:
the evolution-narrative Warning vocabulary is defined only by
EvolutionNarrativeTerms in internal/machinecontract/lexical.go and consumed
directly by internal/index/validator.go; default S quota values are owned by
internal/machinecontract/numeric.go. This file and the Prompts explain writing
intent and give non-exhaustive examples; they copy no machine vocabulary.

0. General principle

The AOCI index is written for models: a model understands the whole system
through the Header rules plus the sum of every section's Entries. An Entry has
five leading layers — file name, tag, F, R, A — and S carries the necessary
information that those five layers cannot express.

Tags and F/R/A/S are cognition semantics and must be generated by the current
model after reading the target file, the index Header, and the necessary
related evidence. Generating, prefilled, assembling, or rewriting semantics
with an AST, symbol extraction, import/include scans, paths, file names,
extensions, regular expressions, templates, rule engines, or batch scripts is
forbidden. Tools may read, chunk and transport, hash, validate, and persist,
but they cannot substitute for model understanding.

1. The F field

Write one short, unambiguous core-responsibility anchor, normally within about
ten words. Semantic completeness takes priority; moderately exceeding the
guideline is acceptable when genuinely needed. Do not translate the file name,
pile up multiple responsibilities, or use bulk template sentences such as
"implements X and provides Y".

F length and wording quality are soft semantic-quality goals: no machine
Warning by character count, no machine hard rejection by character count, no
blocking of automatic Stage, Check, or Apply because of F length. Quality is
improved through the model contract, human calibration examples, Diff review,
and later semantic sampling. (Volumes v1 objects additionally enforce the
FRAS v2 field limits owned by internal/machinecontract.)

2. The R field

List only the strong cross-file relations that must be considered together
when understanding or modifying this file. Tooling dependencies (logging,
generic utilities, framework built-ins) are not listed. Use exact paths or
module names, not natural-language descriptions. Never mechanically copy a
complete import, include, dependency, or call list. Write "-" when no strong
relation exists; do not leave the field empty and do not write "none".

3. The A field

List only the APIs, entry points, or contracts this file exposes externally.
Internal functions, private methods, and symbols used only inside the file are
not listed. Write "-" when there is no external contract; do not leave the
field empty and do not write "none".

4. The iron rule of S (the double question)

Before writing each S statement, ask two questions:

  First: is this statement truly not inferable from the four leading layers
  (file name + tag + F + R + A)?
  Second: does this statement truly affect how a model understands the system
  or safely modifies the code?

Write it only when both answers are yes. Equivalent short form: "Without this
statement, would a model do something wrong?"

5. What S carries (high-entropy content list)

- File-level operational constraints whose violation causes incidents (backup
  requirements, do-not-modify items, execution order);
- exceptions in this file that run against the statistically default practice;
- implicit cross-file or cross-language contracts (two constants must stay
  identical; A's behavior depends on B's configuration);
- lessons that were paid for, stated as current mechanisms without temporal
  narrative;
- necessary boundaries this file explicitly does not support, does not allow,
  or must preserve;
- other current facts that cannot be derived from the file name, tag, F, R, or
  A but must be known before modifying the file.

Boundary division: system-level principles, capability boundaries, and global
prohibitions belong in the Header; whether a file is included or excluded is
governed by Curation; future plans, deferred features, and roadmaps do not
belong in a general-purpose index; S carries only the necessary information of
its own file and never substitutes for the Header or Curation.

6. S length quota (by C importance; the quota is a ceiling, not a target)

Default values (the fallback when the repository declares none) are owned by
internal/machinecontract/numeric.go: C9-C8 up to 600 characters, C7-C4 up to
500, C3-C1 up to 50. A repository may declare its own bands in the index
Header with an English "#S quota" line or the equivalent Chinese declaration;
declared bands use the declared value and undeclared bands fall back to the
machine defaults (gaps are filled, the declaration does not fail as a whole).
The machine gate counts code points, sums S variants, and emits warning-level
violations that pass through without blocking persistence; an unparsable
declaration falls back to defaults and is named in the report layer rather
than silently treated as undeclared.

7. Hard style constraints (never write these, even within quota)

- Temporal information (version numbers, dates, fix traces, evolution
  narratives); the validator warns on the machine-owned narrative vocabulary;
- explanatory content whose removal would not cause a model to err;
- change history: it belongs to version control; history written into an index
  rots into misinformation over time;
- write current cumulative state — what the file is now, not what happened;
  never patch-style increments;
- single line; join long content with semicolons;
- do not write what you are not sure of. A wrong S is more harmful than a
  missing S, because models trust it and skip verification.

8. Calibration examples

The example tags below do not define any project's dictionary; real tags must
follow the current project Header dictionary.

main.go[CRT9OT]: F:Process entry | R:internal/cli/root.go | A:- | S:In MCP mode stdout carries only the JSON-RPC protocol stream; logs must go to stderr
atomic.go[FAT9AT]: F:Atomic write | R:- | A:AtomicWrite | S:The temp file must live in the same directory as the target; the original file must survive a failure

Example one: F only states that main.go is the process entry; R lists only
root.go, which must be considered when understanding the entry; A is "-"
because main.go exposes no reusable API; S keeps only the stdout/stderr
protocol constraint — not derivable from the first four layers, and violating
it breaks MCP communication.

Example two: F only states that atomic.go performs atomic writes; R is "-"
rather than a list of generic dependencies; A lists only the exported
AtomicWrite; S keeps only the same-directory temp file and keep-original-on-
failure safety constraints.

9. S rewriting examples

Bad:  S:This change fixed a parsing bug; it now uses a new regex
Good: S:The three regexes match the platform implementation character for character; changing either side requires three-way sync and a differential test first

Bad:  S:This is the configuration loading module
Good: S:A missing file uses built-in defaults without error; corrupt JSON errors with a manual-repair hint; .aoci stays on the exclusion list to prevent self-ingestion

Bad:  S:This file will support multi-tenancy later
Good: S:-

Bad:  S:This file has no remote upload capability
Good: if this is a system-level capability boundary, put it in the Header; if
it is merely unrelated commentary, do not write it; if the file must forbid
remote sending and violation would leak data, write:
  S:All data is written only to the local repository; adding a remote send path is forbidden
