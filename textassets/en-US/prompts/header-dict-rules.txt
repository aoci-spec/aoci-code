Dictionary discipline (later Entry generation is machine-validated against it; undeclared symbols are rejected):
1. Symbols in B Module and optional D Trait must not contain digits. The first digit in a compact tag is the boundary that begins C Importance.
2. Dictionary values may cover only layers, modules, and traits inferable from the repository profile below. Never invent a module absent from that profile.
3. Preserve existing dictionary items in the current Header. You may add evidenced items, but do not remove an item or change a symbol's meaning without cause.
4. Use multiple tag systems only when the profile shows multiple technical domains, such as backend plus frontend, or code plus a large documentation estate. In that case create separate A/B/D blocks for each domain. Do not force multiple domains into one dictionary, and do not split one domain merely to create more systems. One technical domain needs one dictionary.
5. A and B semantics must not overlap. A Layer answers “what architectural role does this kind of file play?” such as command, core, or test. B Module answers “which business or functional domain owns this file?” such as parsing, validation, or configuration. A concept must not appear in both dictionaries; overlap causes dimension drift and makes a symbol semantically invalid when placed in the wrong dimension.
6. Omit uncertain content. A wrong Header is more harmful than an incomplete Header.
7. Keep numeric declarations machine-readable. On the E Scale line, write each symbol, description, and comparison together, for example L-large>400 M-medium200-400 S-small100-200 T-tiny<100. Digits and comparison operators must remain machine-readable. To customize S quotas, use a separate #S quota: line such as {{.SQuotaDefaultCompact}}. When preserving an existing Header declaration, do not change its numeric boundaries unless the maintainer explicitly requests that change.
