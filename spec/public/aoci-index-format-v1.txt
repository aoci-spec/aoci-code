AOCI Public Cognition Format v1
===============================

Scope
-----

This document defines the public text interoperability boundary for AOCI
cognition. It describes observable syntax and compatibility; it does not
describe Planner derivation, patent material, commercial policy, or research
protocols. The current parser, validator, and machine contracts in the compiled
binary remain the executable authority.

Encoding and layout
-------------------

Cognition assets are UTF-8 text. Readers accept LF and CRLF; writers preserve
the established line-ending form when the applicable write contract requires
it. The configured `index_path` is the only discovery entry.

A Legacy document contains one header followed by directory sections and
object Entries. A Volumes root begins with the exact Root Manifest marker and
declares versioned Root, Meta, Code, and optional Database assets. Volume paths
are repository-relative and are validated before use. The Volumes contract
defines layout selection and consistency rules.

Code section roots and clone relocation
---------------------------------------

The absolute path token in a Legacy or Code Volume directory section header is
the structural coordinate captured when that section family was created. It is
historical text, not the runtime repository root, a source-access path, or a
semantic object identity. The runtime repository root is resolved for each
invocation; an explicit `--repo` binds it directly and takes precedence over
repository discovery, as defined by the CLI runtime contract.

Readers logically relocate directory sections from their consistent historical
root to the current runtime root and derive repository-relative object paths. A
Volumes Code object therefore has the canonical identity
`code:<repository-relative-path>`. Moving or cloning a repository requires no
index rewrite, and ordinary reads do not replace historical section roots with
the current machine path. If the historical sections cannot be mapped safely
and unambiguously, path resolution fails closed instead of guessing.

The repository-relative requirement for a Root Manifest declaration such as
`#Volume: ... path=aoci.code.txt ...` applies to the declared Volume asset path.
It does not make a Code Volume directory section header a runtime path or a
Volume declaration. Implementations and integrations must not conflate these
two path fields.

Because historical section roots remain versioned text, a repository intended
for publication should review them for unwanted hostnames, user names, secret
material, or other private topology before its first public commit. Such a
review is a disclosure boundary; it does not change the logical-relocation
contract and is not authorization to edit formal cognition assets directly.

Directory and file names
------------------------

A directory section header is `===`, an optional description, the absolute
directory ending in `/`, and `===`. The path starts at the first `/`, or at a
drive letter followed by `:/`. Readers first apply the original reading, in
which the path ends at the first whitespace, `=`, `(`, or `（` and the rest of
the header is an annotation. When that remainder itself ends the header with
`/`, does not begin with whitespace directly after a complete directory, and
does not start another absolute path, it is the rest of the directory: a
machine-written header for a directory whose name holds one of those
characters, such as `===/work/my project/app/(home)/===`. A header whose
remainder does not end in `/`, follows a complete directory after whitespace,
or starts another absolute path keeps the original reading. Two hand-written
shapes therefore read differently than before, because they are now part of the
directory: an annotation that ends in `/` directly after an unfinished path
segment, and one that begins with `(`, `（`, or `=` directly after a complete
directory and ends in `/`, as in `===/opt/x/(a/b)/===`.

A file name may hold `[`, as in `[...id].jsx`. The original Entry reading is
tried first; when it fails, the tag is the bracket group immediately followed
by `: F:`, and the file name is everything before it. Every consumer of the
tag (dictionary, scale, quota, name normalization) locates it the same way.

Names are written as they are, never escaped. Before it adds a section, a
writer checks that the header reads back to the same directory and that the
section resolves to the directory it was written for, and refuses the Entry
when either fails (a segment that ends in whitespace, for example), naming the
directory. No edit to the Entry clears that refusal, so it is answered as a
stop with the operator's way out (rename the directory, or take its files out
of the index role), never as a repairable candidate, and a planner that can see
it coming withholds the batch instead of asking for Entries it would have to
refuse. A file name that begins with whitespace or holds a backslash is outside
the portable path contract.

Section roots are coordinates, not runtime paths, and the root section anchors
them. A new index begins with its root section: when its first Entry lives in a
directory, the root section is written, empty, ahead of it, and an empty section
is kept for as long as every other directory section lies below it. Relocation
resolves against the common prefix of the sections, which is the repository
root only while a section sits there; an index without one, which earlier
writers could leave behind, may resolve differently in a copy than at its
origin.

Under a root holding one of those characters, the root section spells the root
in full and every later section continues it as the original reading reads it
back, that is, truncated at the character. Every release has written this one
shape, so a reader older than this rule still resolves every section of it whose
own directory name it can read. When the repository root has no header that
reads back to it at all (its first segment begins with `(`, `（`, or `=`, or one of its
segments begins or ends with whitespace), the root section records the root as
such a header reads back, and the index resolves by relocation at the origin
exactly as it does in a copy.

Readers recognise that shape from the text alone, before the runtime root is
consulted, so that the origin and a copy at any other path read it identically;
a reader that trusted the runtime root in place could not guarantee that. The
first directory section reads as the common prefix of the sections under the
original reading and as something else under the extended one, whether that
extended path lies beside the prefix (`/tmp/example project/repo` against
`/tmp/example`) or under it (`/w/(x)/repo` against `/w`); every other section
resolves strictly below the prefix, and none sits at the prefix itself. The first section then resolves at the prefix, whichever
directory its header names, and every other section relative to it, with the
extended reading applied below it. Where the first section is the root section,
which is what this rule writes and the common case before it, that is simply the
correct reading. Where an older writer spelled a directory there instead (the
first file it met lived in one, or under a clean root in a top-level directory
whose name begins with `(`, `（`, or `=`), it used that section as its root section,
and readers keep that view everywhere: the Entries filed under it surface as the
same orphans at the origin and in a copy, and the ordinary repair clears them in
both. The same file name under that section and under the section a repair adds
for the directory it names is two paths, not a duplicate. Nothing is rewritten,
and an index that aligned under an earlier reader aligns under this one.

A reader older than this rule cannot read these names: it takes a bracketed
file name for a malformed Entry, resolves a directory whose name holds one of
those characters somewhere else, and rejects a scope rule that holds `[`. An
index or policy that uses them needs a reader that implements this section.

Object Entry
------------

One managed object is represented by one model-authored line:

  object_name[tag]: F:... | R:... | A:... | S:...

`F` records the core responsibility, `R` strong relationships, `A` externally
observable interfaces or contracts, and `S` non-obvious maintenance
constraints. New Volumes Tags are resolved against the active Meta dictionary.
Dotted Tags remain a Legacy read-compatibility form. Exact object and FRAS
rules are defined by `aoci-object-fras-v2.txt` and
`s-field-discipline.txt`.

The default S quota declaration used by the public starter contract is:

#S配额: C9-8≤600 C7-4≤200 C3-1≤50

Machine authority
-----------------

Numeric limits and machine vocabularies have one executable source in
`internal/machinecontract`. Public text delegates lexical enforcement to
`internal/machinecontract/lexical.go`, including `PublicTextTerms` and
`EvolutionNarrativeTerms`; it does not copy the machine vocabulary into this
document.

Failure and compatibility
-------------------------

Malformed headers, sections, Tags, fields, object identities, Volume
declarations, or unsafe paths fail validation. A reader must not combine an
incoherent Root and Volume snapshot. A format extension requires a versioned
machine contract and compatibility tests before public consumers rely on it.
