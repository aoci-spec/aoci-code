AOCI Cognition Refresh Contract v1 (draft)

Status: candidate contract for R67-A. This contract extends the existing
aoci_overview input and receipt. It does not add an MCP tool, a maintenance
workflow, an Apply state, or a persistent product state machine.

1. Purpose

A normal Agent Run reads Rules once and receives one complete Overview. The
host normally reuses that cognition. AOCI can assess three checkpoint reasons:

- context_compaction: the host reports compaction, or the model knows that the
  complete repository view has been lost;
- semantic_threshold: AOCI's current semantic-change count reaches the project
  threshold; or
- phase_transition: one major work phase has completed and another is about to
  begin.

A function completion, one test run, one tool call, elapsed time, token count,
index digest change, risk path, or minor work step is not a checkpoint reason.
Checkpoint facts advise the Agent; they do not deny an explicit cognition
request. Only check_only=true requests compact status without a body. Every
ordinary explicit Overview requests complete delivery of its scope.

A known Host context-compaction event is not a local-recall uncertainty. The
Host's compacted handoff must not retain or summarize the formal Whole-Index or
any Overview Header, Entry, Chunk, Challenge, or Attestation body. It may retain
only receipt identity, unfinished write or Recovery state needed for safe
continuation, and an instruction to reload immediately. Index semantics or a
receipt copied into that handoff cannot prove that the resumed model's current
cognition is reliable.

2. Project configuration

The team configuration file .aoci/config.json owns:

  cognition_refresh_threshold

The compiled default is 30. Legal values are integers from 1 through 100000.
A repository without the field uses the compiled default. Zero, negative,
non-integer, and out-of-range values fail closed. config.local.json cannot
override this team policy and SaveLocal removes an accidental local copy.

The executable constants in internal/machinecontract/numeric.go are the sole
machine authority for the default and legal range. This document records the
candidate contract; runtime behavior must not parse numeric policy from this
file.

3. Semantic-change count

The count is the size of one deduplicated set of current repository-relative
paths. The set contains:

- real semantic Stale files;
- Actionable Missing files; and
- Pending Curation files.

Editing one path many times still counts once. Modified and new paths share the
same set. Proven format-only and LineEndingOnly changes, Curation exclusions,
deterministic technical skips, Git-ignored content, AOCI runtime assets, paths
restored to Baseline, and objects outside the governance walk do not count.
Deletion remains governed as Orphan and is not added to the semantic count.

The count is derived with the existing Baseline detection, format-only proof,
walk policy, and Curation classification. It does not create another scanner.

4. Host declaration

aoci_overview accepts three optional, additive inputs:

- refresh_reasons: a unique array containing context_compaction and/or
  phase_transition;
- refresh_event_id: a host idempotency key required with refresh_reasons; and
- stable_checkpoint: whether edits, formatting, lint, and required tests have
  reached the nearest stable checkpoint.

semantic_threshold cannot be supplied by a host. AOCI derives it. AOCI also
cannot infer whether a host performed context compaction. Hosts without a
native event adapter must have the Agent make the declaration explicitly.

For backward compatibility, model_cognition_state=invalid paired with a
previously reliable complete receipt is interpreted as a context_compaction
declaration with a deterministic legacy event identifier. Initial cognition
establishment and uncertain receipts returned by governance do not fabricate a
host compaction event. Existing no-argument calls remain valid.

When Host compaction is known, the Host-Agent declares context_compaction
directly with a fresh refresh_event_id. If aoci_rules is no longer reliably
present in current context, it first reads aoci_rules. Before continuing the
business task, it then makes an ordinary complete Whole-Index aoci_overview
request, not check_only and not a cognition probe, follows every exact
next_cursor through completed=true, confirms delivery, and submits one
Attestation from that newly delivered body. Neither the compacted handoff nor a
prior receipt substitutes for this sequence.

5. Checkpoint outcomes and explicit delivery

The executable vocabulary in internal/machinecontract/status.go is authoritative:

- refresh_not_required: the checkpoint recommends reuse;
- refresh_deferred_until_stable: a trigger exists, but semantic work has not
  reached a stable checkpoint;
- refresh_required: run the existing maintenance and alignment gates;
- refresh_ready_for_overview: governance is aligned and a reliable full
  Overview can be established after the required proof.

These are check_only assessment results and metadata on ordinary delivery, not
durable workflow states. Natural-language next actions are localized; machine
values do not vary by Locale. check_only=true always returns compact JSON and
never returns the cognition body.

When check_only is absent or false, the call is an explicit cognition request.
AOCI delivers the complete requested scope whenever it can form one coherent,
verified CognitionSet. It does not suppress the body because a matching receipt
exists, no checkpoint reason is pending, or the semantic count is below the
threshold. Repeated ordinary calls therefore repeat the complete requested
scope. The one exception is the Host-capacity stop of section 12, which answers
a pending compaction refresh this server session has proven the Host cannot
hold. One complete, Host-confirmed, governance-aligned Attestation attempt
advances the receipt generation and consumes pending checkpoint reasons. A
passing Attestation records a reliable receipt. A partial or failed Attestation
records an uncertain receipt and disables a full-system claim without
retriggering the same refresh generation.

An ordinary call carrying delta_since asks for the objects changed since the
delivery it names instead of the complete scope. It is an explicit cognition
request like any other ordinary call, never a checkpoint; when it is served,
when it answers the complete scope with a fallback_reason, and how its
Attestation moves the receipt are owned by aoci-overview-delivery-v1.txt
(Incremental delivery (L5)), specified in 0.2.0-rc2 for a 0.2.x release.

When formal cognition is structurally complete but source governance is Dirty
or Stale, ordinary Overview still returns the complete formal body. It reports
cognition_currency=dirty_or_stale and governance_aligned=false and issues no
reliable model cognition receipt. Current source, tests, configuration, and
database evidence remain implementation truth.

Pending recovery, an unresolved partial cross-Volume commit, an invalid or
missing declared asset, a changed asset during assembly, or any other failure
to form a coherent snapshot stops ordinary delivery with a structured error.
It never returns a mixed body or a compact assessment pretending to be an
Overview.

When aoci_maintain observes the machine threshold, it preserves
semantic_threshold in the current MCP session before Apply advances the
Baseline. Maintain and the aligned aoci_update_entry result expose the existing
refresh_status and refresh_reasons fields additively. An aligned result reports
refresh_ready_for_overview. The Agent completes Verify, Check, and Guide proof
and decides whether its next phase needs an explicit Overview.

6. Required order

When semantic change or another governance blocker exists:

  finish nearest stable work unit
  -> formatting, lint, and tests
  -> aoci_maintain once
  -> resolve repair_required; classify stopped from formal-write/Recovery proof
  -> Verify, Check, and Guide prove aligned
  -> optionally request ordinary aoci_overview when the Agent needs the view
  -> record any new reliable receipt

Known Host context compaction with no semantic change requires the direct
ordinary Overview sequence above. A complete, Host-confirmed attempt consumes
that generation even when Attestation is partial or failed; after that fresh
complete transport the Host continues an existing source-bound task without an
automatic second Overview. A failed initial Attestation also
blocks unbound Root/Meta, Migration, layout-wide, and other system decisions,
but does not prohibit honest answers or task-bound source and test inspection. A
clean phase transition does not by itself recommend retransmission. Multiple
simultaneous reasons merge into one checkpoint assessment. A repeated
refresh_event_id is idempotent; it does not suppress an ordinary explicit body.

7. Receipt and server memory

The existing cognition receipt adds optional fields:

- refresh_generation;
- last_refresh_event_id; and
- pending_refresh_reasons.

The original required fields are unchanged. During one MCP stdio session the
server retains only receipt identity, pending reasons, bounded event IDs, and a
generation number. It never retains the complete index body. One complete,
Host-confirmed, aligned Attestation attempt consumes the merged event and
starts the next counting cycle. Pass records a reliable receipt; partial or
fail records an uncertain receipt and the existing source-bound delivery
guidance. Dirty delivery and a compatibility fallback that omits the full body
do not consume the event or establish a reliable complete-cognition receipt.

8. Compatibility and evidence

- MCP tools/list remains nine tools.
- aoci_overview without arguments requests complete Legacy cognition or the
  complete Volumes all scope on every ordinary call.
- check_only always returns compact JSON and never transmits the index body.
- repeated ordinary Overview calls return the complete requested scope,
  except the Host-capacity stop of section 12.
- an oversized Whole-Index begins the deterministic Entry-boundary continuation
  chain at Chunk 1 according to `overview_delivery.chunk_tokens`; it does not
  first attempt one oversized response.
- Chunk Receipt and Attestation ordinals consume one shared canonical 1-based
  formal Entry/object sequence; Header content, comments, blank lines, markers,
  receipts, and Metadata are excluded.
- a partial or failed chain or Attestation cannot be repaired with Memory,
  source, Spec, direct aoci.txt, historical sessions, Scope, Search, or Entry
  reads before formal acceptance.
- Attestation is not an engineering permission system. A partial or failed
  result prevents a complete-system claim; source-bound investigation and
  engineering remain available under current source/test/CAS/Recovery proof.
- the Ledger schema and existing events remain readable; existing fields
  record tool calls, full Overview reads, semantic files, bytes, tokens, and
  duration.
- Locale changes natural-language descriptions only, never machine fields,
  reasons, statuses, or numeric authority.

9. Volumes v1 scope extension

Volumes v1 reuses this refresh session and adds no workflow state. A receipt-v2
scope identity is the reliability key for the requested dependency closure;
composite identity is reported but does not invalidate an unrelated partial
scope. Every ordinary call delivers the selected dependency closure. Only a
complete, current all delivery establishes reliable full repository cognition.
See aoci-cognition-volumes-v1.txt.

10. Session cognition line on read tools

In Volumes v1, aoci_search, aoci_get_entries, and aoci_header append one
advisory machine line built only from in-process session facts, never from a
filesystem scan:

  cognition: refresh_status=refresh_not_required generation=N

The line is a fact, never a command, and identity drift alone never raises it:
after this session's own governance-aligned writes it stays
refresh_not_required through the cached aligned identity. It escalates only on
the real signals — no delivery yet in this process, or pending declared
reasons — and then names the next step. When the live index identity has moved
past everything the session has assessed, the line does not fabricate a
refresh_status verdict; it reports checkpoint=recommended and points at
check_only, forming a cheap-line → checkpoint → full-recall ladder in which
each level gates the next. Legacy layouts carry no line.

11. Cognition probe

check_only=true accepts two optional, mutually exclusive inputs. probe=true
returns cognition_probe: a deterministic two-question sample of the current
formal Entry sequence, stable within one (index identity, generation) and
bound by a digest. probe_answers submits memory-only answers to exactly that
probe; grading uses the same identity, tag, and core-F criteria as the full
Attestation and returns probe_result pass, fail, or stale. A pass is machine
proof that retained cognition makes a re-delivery unnecessary, and, once
incremental delivery is implemented, the eligibility proof for it: a Host
that holds the base and passed the probe over the current identity may ask
for the objects changed since that base with delta_since
(aoci-overview-delivery-v1.txt, Incremental delivery (L5)); without the pass
the request answers the complete scope. A fail is the
machine evidence on which the host declares context_compaction through the
existing refresh_reasons contract; the probe itself never advances the
generation, never records a reason, and never changes any receipt. A stale
result means the index moved since issuance and is not evidence of loss.
Consulting Search or Get Entries between probe and answer defeats the
measurement and is forbidden exactly as during Attestation.

The probe is available only when no Host compaction event is known. It must not
be issued or answered after a Host compaction, and an answer reconstructed from
a compacted handoff or summary is not retained cognition. A known event takes
the direct declaration and ordinary Overview path above regardless of how much
index-shaped text the handoff appears to contain.

12. Host capacity

A context-compaction refresh asks for one fresh complete Overview, and that
reload assumes the Whole-Index fits the Host's post-compaction context. When it
does not, the reload is itself compacted before it can finish, the refresh is
asked for again, and the session never reaches its task. The MCP server process
outlives Host compactions, so the server records what the Host cannot:

- a compaction reload attempt opens when a fresh complete delivery of the
  complete scope (Volumes all, Legacy repository) starts while a declared
  context_compaction is pending. A later chunk of the same chain advances it.
  A proof half for its body, or any confirmed and attested delivery that
  consumes the pending events, closes it. Scoped deliveries never open an
  attempt: the reload this section protects is the Whole-Index, so an
  unattested small read can never lower the verdict;
- an incomplete Host confirmation without a model proof half does not close
  the attempt. The next fresh compaction declaration still interrupts it.
  The independent model proof path, including a failed semantic assessment,
  retains its existing closing behavior;
- a context_compaction declared with a fresh refresh_event_id while an attempt
  is open is an interruption. It sets the Host-capacity verdict to the
  attempt's estimated tokens (the smallest interrupted size wins) and closes
  the attempt;
- while a declared context_compaction is pending and the verdict covers a scope
  at least as large as the requested one, a fresh complete request answers
  delivery_mode=capacity_stop with
  fallback_reason=host_context_capacity_exceeded instead of a chain. The stop
  carries no body and no cognition level. It consumes the pending events,
  advances the generation with an uncertain receipt, and reports
  refresh_status=refresh_not_required,
  delivery_guidance=full_system_claim_disabled_source_bound_task_continuation_allowed,
  the measured plan, and the verdict. The Host continues the business task
  source-bound without an unqualified complete-system claim and does not retry;
  lowering chunk_tokens bounds one response, not the cumulative context.

The verdict lives in the server session only. It is never persisted, a server
restart clears it, and it changes no identity, receipt format, or tool schema.
An explicit ordinary request made while no compaction refresh is pending still
delivers the complete scope, a scope below the verdict (code, database, meta,
project) still delivers, and continuation and proof calls for a chain the Host
already holds are served as before.

check_only reports delivery_plan (scope, scope identity, Entry count, estimated
tokens, framed-body bytes, chunk_tokens, and chunk count, measured by the
delivery path's own chunk planner) and host_capacity (verdict, failed size,
interruptions, the interrupted chain and how far it got, and
compaction_reload=deliver or capacity_stop for the requested scope) before any
transfer.

Every Overview Ledger event carries delivery_chain_id: a fresh complete
delivery mints it, and its continuations and proof calls inherit it by body
identity. Delivered responses record chunk_index, chunk_count,
delivery_completed, and the refresh_reasons they answered; attestation calls
record host_delivery_status and the attestation result. An interruption
records overview_delivery_interrupted with the interrupted chain and chunk, and
the stop records overview_capacity_stop.
