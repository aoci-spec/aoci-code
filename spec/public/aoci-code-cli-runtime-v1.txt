AOCI-CODE CLI Runtime Contract v1
=================================

Identity
--------

The installed binary is named `aoci`. The canonical Go module is
`github.com/aoci-spec/aoci-code`. The command tree and the exact flags exposed
by the current binary are discoverable through `aoci --help` and command-level
`--help` output.

Global behavior
---------------

`--repo` binds an invocation to a repository root. `--json` selects the
machine-readable output for commands that support it. `--quiet` suppresses
eligible human progress output; it does not change the result or authorization
boundary.

The stable process exit classes are:

  0 success
  1 drift or ordinary check failure
  2 invalid input, index, or governance state
  3 uninitialized repository, configuration, or parameter failure
  10 internal failure

One `--json` invocation emits at most one top-level business result or error
envelope. Human-readable errors are written to stderr. The `aoci mcp` command
uses a direct stdio protocol path described by the MCP runtime contract.

State and writes
----------------

Command help and the live Guide identify whether an operation is observational,
prepares a candidate, requires human interaction, or can update formal assets.
An observational command does not modify the formal index or Baseline unless
its contract explicitly says otherwise, but local audit evidence can still be
written when enabled. Formal writes use the existing validation, lock, CAS,
atomic-write, and recovery pipeline.

Code target planning
--------------------

`aoci cognition plan diff --target-index aoci.code.target.txt` treats the
repository-root target as the conventional generated planning asset. If that
file is absent, the command atomically creates it from the exact active formal
Code Volume before comparing it. It never replaces an existing target. An
explicit alternate target path retains read-only input behavior and must
already exist. Target initialization does not modify formal cognition or the
Baseline and does not authorize Apply.

Default Code target finalization
--------------------------------

`aoci update-entry` with no single-Entry inputs fixes its input to the
repository-root `aoci.code.target.txt`. It recomputes current Code debt, binds
the target Entries to final source hashes, and accepts deletion only through an
exact `#Target-Delete: code:<path>` declaration whose source is absent and whose
formal Entry is an Orphan. Create, update, reuse, and delete use the existing
one-batch validation/CAS/Baseline/Recovery pipeline, and success synchronizes
target from formal Code and consumes every control marker. Omission without a
delete declaration is invalid. The command does not invoke a model. It emits one
structured result; repair-required target content exits 2, a stopped machine or
governance precondition exits 3, and an internal transport failure exits 10.

Supplying any single-Entry input keeps the existing explicit `--path`,
`--entry` or `--stdin`, `--source-sha256`, and optional `--preview` behavior.
Partial single-Entry input fails before formal writes and never falls through
to default target finalization.

Compatibility
-------------

Automation must consume JSON fields, schema versions, exit classes, and live
capability output instead of parsing human prose. A public contract change that
alters these surfaces requires matching compatibility tests.
